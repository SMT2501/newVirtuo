# Virtuo Designs

A multi-page agency website and account-scoped client operations CRM built with React, Vite, Tailwind CSS v4, Firebase Authentication, Firestore, and Firebase Storage. Client-side routing uses wouter.

## Pages

- `/` — Home
- `/about` — About
- `/services` — Services
- `/consulting` — Consulting
- `/portfolio` — Portfolio
- `/pricing` — Pricing
- `/contact` — Contact
- `/faq` — FAQ
- `/admin` — Internal CRM workspace for accounts, contacts, projects, tasks, documents, invoices, and activity
- `/portal` — Client portal for account-scoped projects, documents, signatures, invoices, tasks, and shared activity
- `/project/:shareId` — PIN-protected shared project view for project progress, files, and signing without a client account

## Running locally

```bash
PORT=5000 pnpm run dev
```

## Building for production

```bash
pnpm run build
# Output: dist/public/
```

## Deployment

Configured as a **static** deployment on Replit:
- Build command: `pnpm run build`
- Public directory: `dist/public`
- `public/_redirects` contains `/* /index.html 200` to fix SPA deep-link / page-refresh routing on the host.

## CRM data and Firebase setup

The CRM adds these Firestore collections:

- `accounts` and `accounts/{accountId}/members` — client organization records and access membership
- `projects`, `tasks`, `documents`, `invoices`, and `activities` — account-linked operational records

Internal users require a `users/{uid}` profile with `role: "admin"` or `role: "staff"`. Client logins are linked to an account by setting `users/{uid}.accountId` and adding an `accounts/{accountId}/members/{uid}` document. Existing legacy records that use `clientId` or `ownerId` remain readable by that client.

Before using the new CRM with real client records, deploy the included access controls to the configured Firebase project:

```bash
firebase deploy --only functions,firestore:rules,firestore:indexes,storage
```

The document-signing flow accepts PDFs. A Firebase Callable Function fetches the original private PDF, embeds the signer name and timestamp server-side, stores the completed copy in Firebase Storage, and saves the signature audit event transactionally in Firestore. It is an in-platform electronic signature record, not a certified or qualified e-signature service.

### Project link and PIN access

New projects receive an opaque project link and a high-entropy PIN generated by a Firebase Callable Function. The PIN is never placed in the URL or stored in browser-readable project data. The public page first creates an invisible Firebase anonymous session, then the function validates the PIN and writes a one-hour project access record for that session. Firestore and Storage rules require that record, its matching share version, and an enabled share before serving client-visible project records or signed-document actions.

Before using this flow, enable **Anonymous** sign-in in the Firebase Authentication providers and deploy the Functions alongside the rules:

```bash
firebase deploy --only functions,firestore:rules,storage
```

Rotating the PIN or disabling sharing increments the project share version, immediately invalidating previous anonymous access records. Admins must manually share the link and PIN; no client email is sent by this feature.
